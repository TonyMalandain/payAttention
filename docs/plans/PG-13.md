# Plan — PG-13: "Test alert" is a developer tool, offered only by a developer build

Backlog: PG-13. Product decision: D-037 (`docs/product/decisions.md`, supersedes D-036). Mechanism: ADR-0013 (`docs/architecture/adr/ADR-0013-developer-aids-are-a-build-variant-not-a-setting.md`). Contracts: `interfaces.md` §3, §4, §4.1, §5; `data.md` "Removed keys"; `boundaries.md` (the developer marker); `testing-and-build.md` steps 4 and 6, Layers 3, 3b, 4, and "The developer copy in the real session".
This undoes the setting half of PG-12 (commit 8fb899a, `docs/plans/PG-12.md`). The View field, the named menu item and its visibility line in the indicator stay: they are already the right shape. Only the source of the boolean changes.

**Size: M.** One behaviour, decided mechanism. But it touches a stored contract (a key leaves the schema), the controller's constructor contract, the build, both install paths, the isolation helper, three smoke checks and the README. Each change is shallow.

## What changes, and for whom

- **Calendar owner:** the menu never offers Test alert, and Settings has no switch for it. An install that had the PG-12 switch on shows no Test alert after the update: nothing reads the stored value.
- **Developer:** `npm run sample` always offers Test alert, with no extra step. `npm run install:developer` installs a copy whose menu offers it into the real desktop. `npm run install:local` puts the normal copy back and says it replaced the developer copy. Both take effect at the next login (Wayland).
- **Unchanged:** what Test alert does (`core/testAlert.js`), `Controller.runTestAlert()`, `Extension.runTestAlert()` — ungated in every build (`interfaces.md` §4). The smoke keeps driving the ladder on the normal bundle through `runTestAlert()`.

## The component

There are three homes, each serving its own responsibility.

- **`extension/extension.js` (composition root).**
  - Responsible for: building the controller from the shell's objects, and nothing else.
  - The marker is a fact the shell hands this object (`this.metadata`). Turning it into one boolean dependency is composition. `boundaries.md` names this file as the only reader.
- **`extension/app/controller.js` → `app/view.js`.**
  - Responsible for: deciding, from injected facts, what the UI shows. "Whether the menu offers Test alert" is a whether-to-show decision. It already lives in `buildView` (`showTestAlert: p.showTestAlert === true`). Only its input moves, from `settings.showTestAlert` to a constructor fact.
  - The controller never learns the word "developer" (`boundaries.md`). The dependency is named for what it means to the menu.
- **`scripts/` (build, install, isolation helper).**
  - Responsible for: making bundles and putting them in a home. The second bundle and the choice of which one to install belong here.
- **Has drifted by:** no drift in the code that changes.
  - `isolated_install` hard-codes the one zip path. That was correct while there was one bundle. With two, which bundle a throwaway shell runs becomes a choice. The plan makes the choice an explicit argument at each call site. That is the change itself, not a repair.
- **Rejected placements:**
  - Reading the marker in `app/` or `ui/`: `boundaries.md` forbids it, and `app/` must stay runnable under Node with fakes.
  - Gating `runTestAlert()`: `interfaces.md` §4 forbids it.
  - Removing the menu item's code from `ui/indicator.js`: the developer bundle needs it, and ADR-0013 keeps one code base.
  - Writing the marker into `extension/metadata.json`, even temporarily: `interfaces.md` §4.1 forbids it.

## Seams

1. **`Controller` constructor** (`extension/app/controller.js`). One new required dependency:
   ```js
   * @param {boolean} deps.menuOffersTestAlert whether the menu offers Test alert; fixed for the life of
   *   the controller (decided by the build, interfaces.md §4.1)
   * @throws {TypeError} before building anything, when createAiClient or createAiTicker is not a function,
   *   or menuOffersTestAlert is not a boolean
   ```
   - The guard is its own `if`, placed right after the existing AI guard, before `this._deps = deps;`:
     ```js
     if (typeof deps.menuOffersTestAlert !== 'boolean')
         throw new TypeError('controller: deps.menuOffersTestAlert must be a boolean');
     ```
   - The constructor stores it as `this._menuOffersTestAlert = deps.menuOffersTestAlert;`, next to the other field initialisations, before the `try`.
   - `_render` passes `showTestAlert: this._menuOffersTestAlert` to `buildView`. This replaces `showTestAlert: settings.showTestAlert`.
   - **Misuse designed out:** a composition root that forgets the fact, or passes the raw metadata value (`"true"`, `undefined`), fails at construction in every test run. It does not quietly show or hide the item. There is no setter, so it cannot flip at run time.

2. **`buildView(p)`** (`extension/app/view.js`). No signature change. Change the JSDoc of `p.showTestAlert` to:
   `whether the menu offers Test alert (decided by the build, interfaces.md §4.1)`.
   `View.menu.showTestAlert` is unchanged. Its strict `=== true` stays.

3. **`extension.js`.**
   - A module constant, after `AI_HELPER_ENTRY`, with this comment and value:
     ```js
     // Only the developer bundle's metadata.json has it, strictly true (ADR-0013, interfaces.md §4.1).
     const DEVELOPER_MARKER = 'payattention-developer';
     ```
   - One new entry in the `new Controller({...})` object, after `createAiTicker` and before `launchUri`:
     ```js
     menuOffersTestAlert: this.metadata[DEVELOPER_MARKER] === true,
     ```
   - **Misuse designed out:** anything but a strict `true` is a normal build, which fails toward the product.

4. **`isolated_install`** (`scripts/isolated-shell.sh`):
   ```
   # Installs one bundle into <home>/data and creates the XDG directories an isolated shell needs.
   # <home> must be <repository>/.smoke-home or <repository>/.sample-home (ISOLATED_HOMES).
   # <bundle> is normal (dist/<UUID>.shell-extension.zip) or developer (dist/<UUID>.developer.shell-extension.zip, ADR-0013).
   isolated_install <home> <bundle>
   ```
   - The home is validated first, exactly as today.
   - Then the bundle, before any `mkdir`. Anything other than `normal` or `developer`, including a missing argument, prints `isolated_install: refusing bundle '<value>': it is normal or developer` to stderr and returns 1. The word "refusing" matters: `isolation-check.sh`'s `refuses` helper looks for it.
   - **Misuse designed out:** there is no default, so every call site states which bundle its shell runs. A smoke cannot silently run a developer copy, and the sample cannot silently run a normal one.

5. **`scripts/install.sh` arguments:**
   ```
   USAGE='Usage: npm run install:local, or npm run install:developer for the copy whose menu offers Test alert'
   ```
   - Step "a. Arguments, all checked before anything changes", placed before the existing step 1 (the preflight), in `uninstall.sh`'s style:
     - `--developer` sets `bundle=developer`. The default is `bundle=normal`.
     - `-h|--help` prints USAGE and exits 0.
     - Anything else prints `install: unknown option '<arg>'. Nothing was changed.`, then USAGE, to stderr, and exits 2.
   - `package.json` gets `"install:developer": "bash scripts/install.sh --developer"`, right after `install:local`.
   - **Misuse designed out:** an unknown option never builds or installs anything.

6. **`scripts/build.sh`:** it always makes both bundles. There is no option, so a normal build can never be stale next to a fresh developer one. Fixed names:
   - `ZIP="dist/$UUID.shell-extension.zip"` (unchanged) is always the normal bundle;
   - `DEV_ZIP="dist/$UUID.developer.shell-extension.zip"`;
   - `MARKER=payattention-developer`.

## Steps

There are no repair steps. The code that changes is in good shape, and its behaviour is covered: `view.test.js`, `controller.test.js` "test alert", the smoke's `2c-menu-test-alert`, the sample's `3b-test-alert`, `prefs.test.js` "existing", and `uninstall-check.sh`.

The steps are ordered so the full sequence is green after each one. The developer bundle exists, and the sample runs it, before anything starts reading the marker. Run `npm run lint` and `npm test` after every step. Run `npm run build && npm run smoke` after Steps 1–5, as each one says.
