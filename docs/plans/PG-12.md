# Plan — PG-12: "Test alert" is hidden from the menu unless the owner turns it on

Backlog: PG-12. Product decision: D-036 (`docs/product/decisions.md`). Spec: `docs/prd/meeting-guardian.md` §5 Top bar (the menu) and §6 Settings. The owner, word for word: "do we still have the "test alert" option in the menu? If so, we should remove it or make it flag-triggered. Useless in prod".
Architecture: `data.md` (the schema; ADR-0003), `interfaces.md` §3 (Controller ↔ UI: the View), §4 (the Extension object's `runTestAlert()`, used by the smoke), §5 (keys may be added; no ADR needed for an addition), `boundaries.md` ("UI must not decide … whether to show something"), `testing-and-build.md` Layer 3b (sample viewing aids are ordinary setting values).

**Size: M, not S.** One behaviour, but it touches a stored contract (a new GSettings key) and eight places: core defaults, `app/view.js`, `app/controller.js`, `ui/indicator.js`, `prefs.js`, the sample script and its check, the smoke ladder, the uninstall check, and the README.

**Gate before Step 1:** the architect adds the `show-test-alert` row to `data.md` (exact row under "For the architect" below). `interfaces.md` §5 already allows adding a key, so this is recording, not a new decision. If the row is not in `data.md` when Step 1 starts, stop (see "Stop and escalate if").

## What changes, and for whom

For the calendar owner:
- The everyday top-bar menu no longer shows "Test alert".
- Settings → Alerts → Behaviour gets a switch, **Show Test alert in the menu**. It is off by default, also on an existing install, because the key is new and an unset key reads its default.
- Turning the switch on shows the item within a second, without a re-login. Turning it off hides it.
- `npm run sample` turns it on in its throwaway settings, so the sample still offers Test alert.
- `--purge` erases it like every other setting.
- README "First five minutes" step 4 says to turn the switch on first.

What does not change: what Test alert does (`core/testAlert.js`, the ~30 s ladder), the controller's `runTestAlert()`, and the Extension's `runTestAlert()` (`interfaces.md` §4).

## The component

- **Responsible for (`app/view.js`):** turning plans, judged meetings and health into exactly what the UI draws. Every "whether to show" decision is made here.
- **Responsible for (`ui/indicator.js`):** drawing the top-bar countdown and the menu from `View.indicator` and `View.menu`, and reporting clicks. It decides nothing.
- **Has drifted by:** no drift. The menu's fixed items (Test alert, Settings) are built once in the indicator's constructor. That was correct while they were always shown. Once one of them depends on a setting, whether it shows is a "whether to show" decision, so it must come from the View, like `menu.status` and `menu.aiStatus` already do.
- **This change belongs here because:**
  - the setting is an ordinary owner setting. It lives with the other owner settings: `DEFAULT_SETTINGS` (one source of defaults), the schema, `SETTINGS_KEYS` (derived automatically), and the store's reader (reads every `SETTINGS_KEYS` entry automatically);
  - `app/view.js` decides whether the menu offers the item. The controller passes it the setting, exactly as it already uses `settings.soundEnabled`;
  - `ui/indicator.js` only applies `visible`, like `_status` and `_aiStatus`.
- **Rejected placements:**
  - Reading GSettings in `ui/`: `boundaries.md` forbids `ui/` any GSettings import.
  - Deciding in the indicator from a raw settings value passed through: the UI would decide whether to show something.
  - Gating `Controller.runTestAlert()` or the `runTestAlert` dispatch on the switch: `interfaces.md` §4 makes `runTestAlert()` a stable entry point with two real callers (the menu and the smoke) and "no test-only branch". The switch is about what the menu offers, nothing else. A test alert already running when the switch is turned off runs to its end.

## Seams

1. **`core/defaults.js` `DEFAULT_SETTINGS`** — one new field, placed right after `soundEnabled`:
   ```js
   showTestAlert: false,
   ```
   `SETTINGS_KEYS` derives `{ field: 'showTestAlert', key: 'show-test-alert', kind: 'bool' }` from it. `StoreReader.readSettings()` reads it with no code change. `StoreReader`'s `'changed'` handler already calls `onChange` for every key not in `INTERNAL_KEYS`, so `Verdicts` reloads its inputs on a flip with no code change.
   - **Misuse designed out:** there is one source for the default. `schema.test.js` already fails if the schema's default differs, or if the schema has a key that `DEFAULT_SETTINGS` lacks.

2. **`core/types.js` `Settings` typedef** — add `showTestAlert:boolean` after `soundEnabled:boolean`.

3. **`app/view.js` `buildView(p)`** — one new input and one new output field.
   - Input JSDoc, after `p.aiStatus`:
     ```js
     * @param {boolean} p.showTestAlert whether the menu offers Test alert (the show-test-alert setting, D-036)
     ```
   - The `View` typedef's `menu` becomes:
     ```js
     menu: {status: string|null, aiStatus: string|null, showTestAlert: boolean, meetings: MeetingRow[], signature: string}
     ```
   - The value is computed as `showTestAlert: p.showTestAlert === true`, placed between `aiStatus` and `meetings` in the returned `menu` object.
   - It is not part of `signatureOf`: the rows are unchanged when the switch flips, so the menu rows are not rebuilt.
   - **Misuse designed out:** a caller that forgets the field, or passes anything other than `true`, gets the item hidden. That is the product default (D-036). The item can never appear by accident.

4. **`app/controller.js` `_render`** — passes `showTestAlert: settings.showTestAlert` to `buildView`, after `aiStatus`. `settings` is already destructured from `this._verdicts.inputs` there. No other controller change. `UiAction` is unchanged.

5. **`ui/indicator.js` `Indicator`** — no signature change.
   - In `_init`, replace the bare `this.menu.addAction('Test alert', …)` with:
     ```js
     this._testAlert = this.menu.addAction('Test alert', () => dispatch({ type: 'runTestAlert' }));
     this._testAlert.name = 'payattention-menu-test-alert';
     this._testAlert.visible = false;
     ```
     It stays in the same place: after the separator, before Settings. Starting hidden means nothing flashes before the first render.
   - In `update(indicator, menu)`, add `this._testAlert.visible = menu.showTestAlert;` right after the two `_aiStatus` lines. It must come **before** the `if (menu.signature === this._signature) return;` early return. If it came after, a flip would show only when a meeting row also changed.
   - **Misuse designed out:** the indicator holds no flag of its own. Whether the item shows is exactly the last View.

6. **Schema** `extension/schemas/org.gnome.shell.extensions.payattention.gschema.xml` — a new key right after `sound-enabled`:
   ```xml
   <key name="show-test-alert" type="b">
     <default>false</default>
     <summary>Show Test alert in the top-bar menu</summary>
   </key>
   ```

7. **`prefs.js`** — in the Alerts page's Behaviour group, right after the sound switch row:
   ```js
   const testAlert = new Adw.SwitchRow({ title: 'Show Test alert in the menu' });
   settings.bind('show-test-alert', testAlert, 'active', Gio.SettingsBindFlags.DEFAULT);
   behaviour.add(testAlert);
   ```
   The title is D-036's wording, exactly. There is no subtitle.

## Already checked

- **A flip reaches the screen with no new wiring.**
  - `StoreReader` calls `onChange` for every non-internal key.
  - `Verdicts._onStoreChange` → `_loadInputs` re-reads settings into `inputs`.
  - The controller ticks every 1000 ms (`extension.js`, `new Ticker(1000, …)`) and reads `this._verdicts.inputs.settings` in `_render`.
  - The cost of a flip is one re-judge, the same as toggling `sound-enabled` today. AI answers are keyed by fingerprint, so a re-judge asks the AI nothing new.
- **The smoke never uses the menu item to run the ladder:** it calls `stateObj.runTestAlert()` at `alert-ladder.js:202`, `:642` and `:724`.
- **The menu's own tests do not care about the item:**
  - `2-menu-verdict` and `2b-menu-travel` find rows by `PopupSubMenuMenuItem` and title;
  - `checkFailedConstruction` counts menus by name.
  - Hiding the item affects none of them.
- **`schema.test.js` covers the new key automatically:** type and default from `SETTINGS_KEYS`, every key has a summary, and there are no other keys. A boolean needs no `RANGES` entry.
- **The prefs `existing` scenario** finds rows by title, which is the established way for the Alerts page (its rows have no names).
- **`--purge`** runs `dconf reset -f` on the whole settings path (`scripts/uninstall.sh` around line 151). `uninstall-check.sh` `3-purge` asserts the path is empty afterwards.
- **Ordering in the indicator:** `update` sets `_status` and `_aiStatus` visibility before the signature early return. The new line follows the same rule.
- **Identifying information:** none in this plan. The fixture data stays `example.test` / `sample.test`.
